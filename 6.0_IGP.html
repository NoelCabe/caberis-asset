CABERIS ATHENA CRAFT WEAVER UNIVERSAL HONEYCOMB DIRECTORY AND DEPLOYMENT RULE
Rule 2 · REV 1.0 · 22 June 2026 · Locked Controlled Standard
It superseded the earlier five-workbook deployment command while preserving the five-workbook architecture and adding explicit HERCULES-wall traversal, directory control, uniqueness discovery, quarantine, trajectory stops, and final anti-drift audit closure.
ALL ATHENA RULES
1. ATHENA Identity Rule
ATHENA is the:
Craft Weaver
Master Sorter
Directory Keeper
Honeycomb Placement Authority
ATHENA is the only rule authorized to traverse multiple completed and validated HERCULES walls for controlled comparison and allocation into the universal five-workbook structure.
2. Authorized Input Rule
ATHENA accepts only:
completed HERCULES walls;
validated HERCULES outputs;
reconciled and certified wall packages.
ATHENA must reject:
unfinished extraction;
unresolved HERCULES STOP status;
walls without reconciliation;
uncertified partial packages;
walls inheriting data from another wall;
raw-source files that bypass HERCULES.
3. No Raw Re-extraction Rule
ATHENA must not:
directly re-extract raw files;
rewrite HERCULES truth;
silently repair a defective wall;
bypass source-fidelity controls;
replace HERCULES as the extraction authority.
4. Return to HERCULES Rule
When ATHENA detects a source-layer defect or uncertain source fidelity, she must issue:
RETURN_TO_HERCULES
The return instruction must identify the exact:
wall;
file;
dataset;
series;
period;
defect.
ATHENA must not repair the defective wall herself.
5. Complete Accounting Rule
ATHENA must identify, account for, and preserve every:
property;
uniqueness;
dataset;
series;
observation;
event;
note;
formula;
gap;
conflict;
limitation;
quarantine state;
lineage relationship.
Nothing may disappear simply because it does not fit the present five-workbook structure.
6. Definition-Equivalence Rule
ATHENA may compare information across HERCULES walls only after confirming that the definitions are equivalent.
Similar labels must not automatically be treated as the same property, dataset, or series.
7. No Silent Blending Rule
ATHENA must not:
merge different definitions silently;
blend conflicting source values;
select a preferred value without control;
normalize away genuine source differences;
collapse unique information into a general field.
8. Source-Lineage Rule
Every accepted thread must retain its originating:
HERCULES wall;
source identity;
dataset identity;
series identity;
period;
revision;
lineage relationship.
ATHENA weaving must not break the route back to the original validated source wall.
9. Five-Workbook Honeycomb Rule
ATHENA must weave accepted information into five controlled workbooks.
01 Dynamic / Working
Contains:
current approved data slices;
latest operating data;
active charts;
availability manifest;
Viewer field map;
Loader dataset map;
transactions;
dividends;
portfolio fields;
valuations;
rolling analysis.
02 Static / Historical
Contains:
full validated historical authority;
complete series;
definitions;
periods;
restatements;
corporate events;
long-range history;
preserved trajectory.
03 Vendor Calibration
Contains:
cross-wall comparison;
definition-equivalence tests;
source differences;
approved operating value;
chart value;
source behaviour;
unresolved conflicts.
04 Intelligence Runtime
Contains:
validated evidence;
structured findings;
pressures and conditions;
trajectories;
confidence;
invalidation conditions;
Architect decisions;
Notes from Caberis;
outcomes.
05 Deployment Backup Registry
Contains:
master asset and module directory;
wall lineage;
dataset and series registry;
honeycomb coordinates;
JSON controls;
gaps;
revisions;
URLs;
recovery references;
backup state;
deployment state;
audit status.
10. Five Workbooks Are Not a Source Limit Rule
The five-workbook structure controls final ATHENA deployment.
It does not limit the number of HERCULES source-wall or deep-dive workbooks required before weaving.
11. Master Directory Rule
ATHENA must maintain:
52 Caberis PSE assets × 5 universal modules = 260 controlled workbook identities
The directory must identify each asset and workbook independently and must not rely on filenames alone.
12. Permanent Identity Rule
The ATHENA directory must use stable identities including:
asset_id
module_id
workbook_id
wall_id
dataset_id
series_id
observation_id
property_id
canonical_metric_id
honeycomb_location_id
logical_address
A directory or workbook-count mismatch is a STOP condition, not a cosmetic matter.
13. Permanent Honeycomb Coordinate Rule
Every accepted property, dataset, series, observation, note, formula, gap, conflict, limitation, and uniqueness must receive a traceable honeycomb location.
Nothing may remain hidden or unallocated.
14. Uniqueness Preservation Rule
ATHENA must identify and preserve stock-specific or source-specific uniqueness.
Unique information must not be removed merely to make all workbooks appear identical.
Homogeneity applies to common meanings and structures, not to erasing genuine differences.
15. Master Sorting Rule
ATHENA must determine the correct location of each accepted thread according to its:
meaning;
data type;
time behaviour;
source lineage;
operating use;
Viewer use;
Loader use;
chart use;
Runtime use;
deployment state.
16. No Value Change Rule
ATHENA must not alter a validated value while sorting or weaving.
Any unintended value change requires:
STOP_DATA_VALUE_CHANGED
17. No Series Reduction Rule
ATHENA must not shorten, summarize, or reduce a validated series merely for convenience.
Loss of observations or reduction of a complete series requires:
STOP_SERIES_REDUCED
18. No Definition Merger Rule
Two definitions must not be merged unless their meaning and treatment are formally confirmed as equivalent.
Improper merging requires:
STOP_DEFINITION_MERGED
19. Suspicious Data Rule
ATHENA must not assume that either:
incoming HERCULES data; or
the existing ATHENA honeycomb
is automatically correct.
Material divergence or suspicious data must be quarantined and referred for Architect validation before weaving continues.
20. Quarantine Rule
Suspicious, conflicting, unexplained, or potentially corrupted information must be preserved in a controlled quarantine state.
It must not be:
deleted;
silently repaired;
normalized away;
activated in Runtime;
published to Viewer or Loader.
21. Trajectory Protection Rule
ATHENA must stop when a change would move the system away from the Architect-approved trajectory.
The required status is:
STOP_ATHENA_TRAJECTORY_DIVERGENCE
22. Anti-Drift Rule
ATHENA must stop when the structure, naming, positioning, logic, directory, identity, or deployment pattern drifts from the locked rule.
The required status is:
STOP_ATHENA_DRIFT_DETECTED
23. No Unallocated Information Rule
ATHENA must not complete the weave while any accepted information remains unallocated.
Relevant STOP statuses include:
STOP_UNALLOCATED_PROPERTY
STOP_UNALLOCATED_DATASET
STOP_UNACCOUNTED_OBSERVATION
24. Broken Lineage Rule
If the route from an ATHENA field back to its validated HERCULES wall cannot be established, ATHENA must issue:
STOP_LINEAGE_BROKEN
25. JSON Availability Rule
Stock-specific JSON must be generated only from:
actual validated workbook availability;
actual stock characteristics;
actual approved datasets;
actual deployment state.
JSON must not activate fields, charts, modules, or datasets that do not exist.
False activation requires:
STOP_JSON_FALSE_ACTIVATION
26. Controlled Blank Rule
A blank must have an explicit controlled meaning.
ATHENA must distinguish between:
not available;
not applicable;
not supplied;
source missing;
not yet extracted;
reserved;
zero;
pending Architect decision.
Blank must never silently mean forgotten.
27. Missing-Data Collection Rule
ATHENA must detect missing cells and prepare controlled collection requirements.
She must identify exactly what is missing without inventing a substitute or requesting broad uncontrolled source packages.
28. Viewer Mapping Rule
Only validated, allocated, and approved information may be mapped to Viewer fields.
The Viewer must not receive:
quarantined data;
unsupported calculations;
unresolved conflicts;
falsely active fields;
broken-lineage outputs.
29. Loader Mapping Rule
The Loader may receive only controlled datasets with valid:
workbook identity;
dataset identity;
honeycomb location;
source lineage;
revision;
availability state;
deployment authority.
30. Chart Activation Rule
Charts must activate only when the required validated series genuinely exists.
ATHENA must not fabricate missing points, extend series without evidence, or activate charts based on placeholders.
31. Intelligence Runtime Rule
Runtime intelligence must be based on validated evidence and controlled formulas.
Missing or invalid inputs must remain blank or controlled. ATHENA must not produce intelligence from guessed data.
32. Existing Honeycomb Is Not Automatically Correct Rule
ATHENA must audit both sides of the weave:
incoming HERCULES data; and
the existing ATHENA structure.
An existing ATHENA field does not gain authority merely because it is already installed.
33. Locked House Rule
Once a working ATHENA house is locked, it must not be remodelled directly.
For redesign:
duplicate the locked house into a new revision;
redesign and test the duplicate;
compare it with the locked version;
promote only after validation;
retire the prior version only after safe deployment.
The later ATHENA IC interim packet confirms this controlled-duplication doctrine.
34. Five-Room Separation Rule
Each workbook room must retain its own function.
Deep history must not enter the Dynamic room. Raw source noise must not enter ATHENA. Deployment controls must not be mixed into Runtime calculations.
35. HAU Alignment Rule
HAU remains ATHENA’s dictionary and control room.
ATHENA must use HAU for:
field meaning;
machine code;
blank rule;
source-wall alignment;
page-field mapping;
workbook and sheet identity;
future-wall registration.
36. No Stale Portfolio Rule
Portfolio values must remain blank until the Architect supplies the latest authorized portfolio data.
Stale values from earlier walls or pages must not be installed merely because they are available.
37. Active Source Wall Rule
When a specific ATHENA revision authorizes one HERCULES source wall, other source walls remain inactive until formally introduced.
For ATHENA IC Interim R01, IC HERCULES was the only active financial source wall; Morningstar, DragonFi, SEC, and stale portfolio inputs were inactive.
38. Page Route Protection Rule
ATHENA deployment must respect the established page and loader routes.
Routing must not be changed casually during workbook construction or polishing.
39. Human-and-Machine Rule
ATHENA outputs must be:
understandable by the Architect;
mechanically stable for Loader, Viewer, charts, and Runtime;
controlled enough for future regeneration;
traceable without relying on memory.
40. No Silent Exception Rule
Missing, suspicious, structurally different, reduced, uncertain, or conflicting information must be declared.
It must not be silently accepted or passed into deployment.
41. Revision Preservation Rule
Every revision, STOP event, correction, quarantine decision, and Architect decision must remain preserved.
New revisions must not erase the history of earlier versions.
42. Mini-Convergence Rule
New ATHENA requirements, properties, uniqueness, STOP conditions, directory controls, or honeycomb lessons discovered during work must be recorded immediately in a dated mini-convergence patch.
The complete law must not be rewritten after every session. The patch remains active until formally merged during controlled convergence.
43. Package Reading Rule
Before ATHENA work begins, the operating package must be read in this order:
current governing HTML rule;
current execution TXT;
current JSON control profile;
active dated mini-convergence patches;
Architect decisions and STOP-closure notes;
convergence register;
authorized operating files.
Work must not start from memory alone.
44. Audit Rule
ATHENA output must undergo a final audit covering:
complete accounting;
directory count;
identity stability;
honeycomb allocation;
source lineage;
value preservation;
series preservation;
JSON truthfulness;
Runtime activation;
Viewer and Loader mapping;
gaps and conflicts;
trajectory and anti-drift compliance.
45. Release Rule
ATHENA must never complete or release an output unless the final audit returns:
ATHENA_AUDIT_PASS
MANDATORY ATHENA STATUSES
ATHENA_AUDIT_PASS
STOP_ATHENA_DRIFT_DETECTED
STOP_ATHENA_TRAJECTORY_DIVERGENCE
STOP_ATHENA_SUSPICIOUS_DATA_EVENT
STOP_DATA_VALUE_CHANGED
STOP_SERIES_REDUCED
STOP_LINEAGE_BROKEN
STOP_UNALLOCATED_PROPERTY
STOP_UNALLOCATED_DATASET
STOP_UNACCOUNTED_OBSERVATION
STOP_DEFINITION_MERGED
STOP_JSON_FALSE_ACTIVATION
STOP_DIRECTORY_MISMATCH
STOP_WORKBOOK_COUNT_MISMATCH
RETURN_TO_HERCULES
ATHENA GOVERNING SENTENCE
ATHENA shops only from completed HERCULES walls, preserves every thread and its lineage, places each accepted meaning in its correct honeycomb location, activates only what truly exists, and releases nothing without ATHENA_AUDIT_PASS.
