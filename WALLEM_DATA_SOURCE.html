THE OCRA RULE

WORD FOR WORD
THE OCRA RULE:

OCRA — ONE CODE RULE ALL

One Code Rule All means one controlled codebase must serve the complete Caberis deployment without separate drifting versions.

The same code must govern:

desktop;
tablet;
mobile;
page layout;
components;
interactions;
hover, lift, and shadow behaviour;
modal or lightbox behaviour;
navigation;
responsive adjustments;
Loader, Viewer, and Runtime connections.
Locked OCRA Principle

Do not create separate desktop and mobile codes. Do not duplicate the page into independent versions. Use one controlled code that adapts responsively while preserving the same identity, function, data connection, and behaviour across all devices.

OCRA Anti-Drift Rules
One page must use one master code.
Desktop and mobile must not become separate systems.
Responsive CSS may change arrangement, spacing, and scale, but not function or identity.
A correction must be made in the master code, not patched into only one device view.
Buttons, cards, modals, navigation, and loaders must retain the same controlled behaviour.
Mobile must not lose required content or functionality.
Desktop must not contain features absent from mobile unless technically impossible and formally declared.
Duplicate code blocks, conflicting media rules, and device-specific copies must be removed.
The code must remain reusable across the controlled Caberis architecture.
Any change that breaks cross-device consistency is an OCRA drift condition.
OCRA Governing Sentence

One code. One identity. One function. All devices.

OCRA is not an ATHENA data-sorting rule. It is the universal Caberis deployment and interface rule that ATHENA outputs, Viewer pages, Loader pages, MONETA tools, and other Caberis systems must follow.

LOCKED INSTALLATION CONTROL

NO HEADER LOGO
Governance use: This rule is the continuing OCRA authority for Caberis page creation, validation, correction, and anti-drift review. Any future improvement must be recorded through an updated controlled revision rather than silently changing this installed doctrine.

18.5 Third-Party Visual Cohesion Rule

Third-party components, references, widgets, charts, embeds, feeds, and external tools must be integrated into Caberis through a controlled visual chamber that preserves Caberis identity, spacing, hierarchy, readability, and long-term page cohesion.

The third-party component must remain technically isolated where required, but the surrounding Caberis structure must make the complete page appear intentional, stable, and professionally unified.

The integration must:

preserve the approved Caberis page skin;
use a controlled outer container around the third-party component;
maintain consistent page width, radius, spacing, borders, and shadows;
identify the external provider clearly;
separate Caberis content from third-party content without making the page look disconnected;
avoid abrupt changes between light Caberis panels and dark embedded widgets;
use an approved transition chamber, data shell, frame, or visual buffer where needed;
maintain balanced spacing above, below, and beside the component;
prevent the external widget from controlling the complete page appearance;
avoid temporary-looking patches or isolated dark boxes;
prevent provider branding, widget controls, or internal layouts from overlapping Caberis content;
preserve usable height on desktop, tablet, and mobile;
avoid excessive empty space when the component loads slowly or fails;
include a controlled loading state;
include a controlled unavailable or fallback state;
remain readable if the provider changes its internal presentation;
avoid depending on fragile internal selectors inside the third-party component;
use stable official provider addresses only;
retain provider attribution and legal notices;
not present third-party information as Caberis-generated;
not allow third-party styling to redefine Caberis colors, typography, buttons, or page hierarchy;
remain maintainable when provider widgets are updated, restricted, replaced, or discontinued.

External components may supply information, but Caberis must control the surrounding identity, structure, and user experience.

18.6 Third-Party Longevity Rule

The Caberis page must remain stable and usable even when the provider changes:

internal colors;
typography;
controls;
branding position;
widget height;
loading behaviour;
symbol coverage;
responsive layout;
data availability.

The page must rely on the official embed boundary, not on undocumented internal widget styling.

The integration must remain maintainable if the provider:

updates the widget;
restricts access;
changes the visual presentation;
replaces the component;
suspends the service;
discontinues the widget.

18.7 Third-Party Loading and Failure State Rule

A third-party component must not leave:

a blank panel;
a broken frame;
uncontrolled error text;
an empty dark area;
excessive unused height;
overlapping loading content.

The page must provide a controlled loading state and a controlled unavailable or fallback state when the external information cannot be displayed.

The exact fallback wording must be approved before installation.

19.4 Long-Page Mobile Navigation Rule

For long Caberis pages, mobile users must not be required to scroll continuously through the complete page to locate major sections.

A controlled lighthouse, compact section navigator, floating directory, collapsible index, or equivalent mobile-access system must be provided where page length makes direct navigation difficult.

The navigation must:

identify all major page sections;
allow direct movement to each section;
remain usable on mobile, tablet, and desktop;
avoid covering essential content;
provide a clear return to the top or main directory;
use the same controlled page code;
preserve all content and functions;
not create a separate mobile version;
not remove sections merely to reduce scrolling.

Long pages must remain navigable, not merely responsive.

19.5 Mobile Image Integrity Rule

Caberis images must remain fully visible, proportionally correct, and accessible across desktop, tablet, and mobile devices.

Images must not be unintentionally cropped, stretched, compressed, clipped by margins, hidden by fixed-height containers, pushed outside the mobile viewport, or reduced until labels or technical details become unreadable.

Required default behaviour:

responsive width;
max-width: 100%;
automatic height;
preserved aspect ratio;
centered positioning;
no horizontal overflow;
consistent mobile side margins;
captions and labels retained;
technical images shown completely.

Technical, evidence, diagram, machinery, screenshot, and document images should default to:

object-fit: contain;
height: auto;

object-fit: cover should be used only where intentional decorative cropping is approved.

Images must adapt to the screen without losing their content, proportion, or meaning.

19.6 Many-Image Mobile Gallery Rule

Where displaying all full-size images would create excessive scrolling, the page should provide a controlled:

gallery;
lighthouse;

Required behaviour:

no image is silently removed from mobile;
images are not combined into one compressed image merely to save space;
the same code controls all devices.

SECTION 23

EVOLVING FRAMEWORK
23. CABERIS SIGNATURE INTERFACE SYSTEM — EVOLVING BRAND FRAMEWORK

23.1 Status

The Caberis Signature Interface System is an evolving brand framework governed under OCRA. It is not declared permanent or final. It will develop through controlled real-work testing, Architect review, approved revision, and preservation of successful interface patterns.

23.2 Purpose

The framework establishes a recognizable Caberis visual and interaction language across governance tools, technical systems, project consoles, desktop pages, tablet layouts, and mobile interfaces while preserving the individual identity and functional purpose of each system.

23.3 Controlled Caberis interface family

Caberis interfaces may share:

clear doctrine and revision hierarchy;
controlled deep-background and high-contrast presentation;
structured panels, cards, borders, spacing, and status controls;
consistent glossary, section-navigation, return, and mobile-access behaviour;
restrained hover, lift, shadow, glow, and motion;
readable typography and evidence-first hierarchy;
responsive behaviour under One Code Rule All;
accessible focus, reduced-motion, and print handling;
functional design without unnecessary decoration.

23.4 System identity

Each governance or Caberis tool must retain its own name, function, doctrine, revision, and operational identity. Shared Caberis presentation must not cause HERCULES, ATHENA, OCRA, APOLLO, IGP, WARD, ORION, the Architect Console, or another system to appear as the same doctrine.

23.5 MONETA naming boundary

MONETA is the Caberis finance and fintech governance identity. The words MONETA skin, MONETA theme, MONETA launcher, or similar presentation shorthand must not appear as the formal design identity of non-finance systems. Informal internal design shorthand must be replaced by the correct Caberis or system-specific interface identity. Legitimate references to MONETA as finance governance remain unchanged.

23.6 Evolution and anti-drift

A new interface pattern may be tested before it becomes a repeated Caberis pattern. Successful patterns may be preserved through controlled revision. Weak, excessive, inaccessible, or non-functional patterns may be removed after Architect review. No presentation change may silently alter another governance doctrine, rule, instruction, embedded attachment, data payload, or functional purpose.

23.7 Governing sentence

Recognizably Caberis. Function before decoration. One controlled code. Evolve through tested revision. Preserve every doctrine's identity.
